# Лимит 120/мин на `/api/auth/check-token/{token}`: расчёт нагрузки

Лимит ставится на адрес клиента (общая корзина для всех токенов, PR #178), `shared_limit("120/minute", scope="auth_check_token")`.
Прежний лимит `30/minute` считался на каждый URL отдельно, то есть отдельно на каждый токен.

## Откуда берётся нагрузка

`login.html` (`startAuthPolling`) опрашивает адрес раз в 2 секунды, пока открыта вкладка с кнопкой входа через Telegram и вход не завершён:

- 1 вкладка: 60 / 2 = **30 запросов в минуту**.
- Лимит 120/мин на адрес: **4 одновременно ожидающих входа** с одного адреса (120 / 30).
- Прежний лимит 30/мин на токен: ровно один опрос в 2 секунды, без запаса (граничный случай, любая неточность таймера давала 429).

## Ёмкость по адресам

Ожидание входа обычно 10-60 секунд (перейти в Telegram, нажать Start, вернуться): 5-30 опросов на вход.

| Среднее ожидание | Опросов на вход | Входов в минуту с одного адреса (лимит 120) |
|---|---|---|
| 15 с | ~8 | 15 |
| 30 с | ~15 | 8 |
| 60 с | ~30 | 4 |

Одновременность важнее, чем частота: пятый одновременный вход с одного адреса частично получает 429. Клиент 429 не считает
ошибкой (`catch` и следующий опрос), поэтому вход не ломается, а задерживается до освобождения корзины (до минуты).

Адреса с высокой общей нагрузкой: мобильные операторы за CGNAT и офисы за NAT, где один внешний адрес у сотен пользователей. Для них
4 одновременных входа мало, но вход через Mini App внутри Telegram (`/api/auth/token` с `initData`) этот эндпоинт не использует, он нужен только
для входа из обычного браузера.

Забытые вкладки: интервал не останавливается, пока вход не завершён. Одна забытая вкладка на экране входа занимает 30 из 120 запросов
в минуту этого адреса, пока браузер не заморозит неактивную вкладку (Chrome после нескольких минут замедляет таймеры до 1 раза в минуту).

## Нагрузка на сервер

Один опрос: проверка памяти, один запрос в БД по `auth_token`, один по `webapp_auth_requests` (SQLite), порядка 1-3 мс.
Даже 100 одновременно ожидающих входов это 50 запросов в секунду, это не нагрузка. Лимит нужен не для CPU, а чтобы один адрес не
гонял перебор. Перебор токена неосуществим: токен это UUID4 (122 бита).

## Рекомендация

- Оставить общую корзину на адрес (она закрывает обход лимита разными токенами).
- Поднять значение до **300/мин** (10 одновременных входов на адрес, 5 запросов в секунду на адрес): запас на NAT и забытые вкладки,
  безопасность не страдает из-за 122 бит токена.
- Если остаётся 120/мин, то снизить частоту опроса на клиенте: 3 секунды и остановка опроса через 5 минут. Это даёт 20 запросов
  в минуту на вкладку (6 одновременных входов) и убирает забытые вкладки.
- Решение за владельцем. Значение хранится в константе `AUTH_CHECK_TOKEN_RATE_LIMIT` в `web_router/_core.py` (PR #178).
