# Требования к PR-B (ссылка продления `/prolong-key/<short_uuid>`)

Записано по решению владельца. PR-B начинается только после PR-A и по отдельному подтверждению.

## Лимиты запросов

- Лимиты на `/prolong-key/*` и `/prolong-key/*/pay` ставятся только через
  `limiter.shared_limit(..., scope="...")` с общим scope или через nginx `limit_req`.
- Обычный `@limiter.limit` не годится: у него корзина считается по URL вместе со значением
  `short_uuid`, и перебор разных токенов с одного адреса обходит лимит
  (воспроизведено на `/api/auth/check-token/{token}`, исправлено в PR #178).
- Структурный тест `tests/test_rate_limit_path_params.py` (PR #178) падает, если лимитируемый роут с
  параметром пути не имеет `scope`. Для PR-B добавить тест «N запросов с разными `short_uuid` с одного
  адреса блокируются» для обоих роутов.
- nginx: `limit_req_zone $binary_remote_addr` считает по `$remote_addr`, поэтому на проде сначала
  должен работать `real_ip_header` для CDN (см. `prod-rollout-checklist.md`, PR-IP).
- Прогрессивная блокировка по `short_uuid` и лимиты ожидающих платежей хранятся в SQLite, не в памяти.

## Токен формы

- HMAC-токен формы НЕ привязывается к IP: только `short_uuid`, nonce и срок действия.
  IP используется только для лимитов и `ip_hash`.

## Прочее

- Зависит от PR-A (режим `payments`) и PR-0. Открытые вопросы владельцу из плана этапа 4 остаются в силе.
