# Сверка платежей с баланса: подход (без кода, необязательная отдельная задача)

Решение владельца: запись намерения для платежей с баланса сейчас не делается. Документ описывает подход на будущее, на включение
`payment_reconciler_mode=retry` он не влияет.

Контекст: сверка зависших платежей из PR-A (`reconciler.py`) ищет строки `pending_transactions` со статусом `paid`,
у которых нет подтверждённой выдачи. Платежи с баланса (`pay_balance`, `pay_referral_balance` в
`webapp/web_router/payments_create.py` и аналогичные в боте) такой строки не создают: сначала списываются деньги
(`deduct_from_balance`), потом генерируется `payment_id` и вызывается `process_successful_payment`. Если процесс
остановился между списанием и выдачей, деньги списаны, а следа платежа нет нигде: сверка его не видит, пользователь ничего
не получил, и возврат делается только в обработчике исключения того же запроса.

## Что нужно

1. **Намерение до списания, в той же транзакции.** `payment_id` создаётся до списания. Списание
   (`UPDATE users SET balance = balance - ? WHERE telegram_id = ? AND balance >= ?`) и вставка строки в
   `pending_transactions` со статусом `paid` и полным `metadata` выполняются одной транзакцией `BEGIN IMMEDIATE`.
   Либо есть и списание, и запись, либо нет ни того, ни другого. Отдельная таблица не нужна: существующая сверка
   увидит такие платежи без изменений. Для реферального баланса то же самое с `referral_balance` и префиксом
   `referral_balance:` в `payment_id`.
2. **Метка способа оплаты.** В `metadata` остаётся `payment_method = Balance|ReferralBalance`, по ней сверка выбирает политику.
3. **Политика для зависшего платежа с баланса** (возраст больше 10 минут, выдача не подтверждена, claim не взят):
   - `extend` при включённой дельте (PR-A): повторить выдачу, повтор идемпотентен.
   - `new` и `gift`: не повторять автоматически, а вернуть деньги через `refund_payment_once` и оповестить админа. Повтор `new` может
     создать второй ключ, а деньги пользователя при этом вернуть безопаснее, чем гадать о состоянии панели.
   - Если claim взят, но выдача не завершена: только оповещение админу и ручное решение через `/recheck_payment`.
4. **Взаимоисключение повтора и возврата.** Возврат идёт под ключом `refund:<payment_id>` в `processed_payments`. Сверка не повторяет
   выдачу, если есть этот ключ, и не возвращает деньги, если уже есть подтверждённая выдача (`transactions.status = paid` и claim).
   Решение «повтор или возврат» принимается под замком `reconciler:ops`, одна копия сверки в момент времени.
5. **Подтверждение выдачи** не меняется: финальная запись `transactions` со статусом `paid` и claim. После успешной выдачи
   `pending_transactions` для баланса получает статус `completed`, чтобы строки не копились.
6. **Совместимость.** Старые платежи без записи остаются невидимыми, ретроактивного поиска нет. Исторические списания можно найти
   только сопоставлением изменений баланса с `transactions`, что вне объёма.
7. **Оповещения.** Каждое автоматическое решение (повтор или возврат) пишется в `ops_alerts` с `payment_id`.

## Порядок внедрения

1. Отдельный PR с п. 1 и 2 (запись намерения), поведение сверки не меняется.
2. Затем п. 3 и 4 в режиме `alert`: сверка только оповещает о таких платежах.
3. После наблюдения на стенде и подтверждения владельца включается автоповтор и автовозврат для платежей с баланса.

## Тесты, которые нужны

- Падение между списанием и выдачей: запись и списание согласованы, сверка доводит `extend` один раз.
- Падение до списания: ни списания, ни записи.
- `new` с баланса зависает: возврат ровно один раз, второго возврата и второго ключа нет.
- Параллельные две покупки с одного баланса при балансе на одну: вторая получает «Недостаточно средств».
- Реферальный баланс: тот же набор.
